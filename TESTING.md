# 🧪 Руководство по тестированию автоматизации Radik.Dev

В данном проекте развернута комплексная система интеграционного, системного и юнит-тестирования на базе **Vitest** совместно с **JSDOM**. Это обеспечивает 100% надежность как логики сборки на уровне NodeJS/Gulp, так и интерактивного пользовательского интерфейса в браузере.

---

## 🚀 Как запускать тесты

- **Одиночный прогон (CI / Продакшен режим):**

  ```bash
  npm run test:run
  ```

  _Применяется автоматически перед каждым коммитом и принудительно внедрен в цепочки деплоя проектов (`deploy:gh`, `deploy:hosting`)._

- **Режим разработки (Watch режим):**
  ```bash
  npm run test
  ```
  _Тесты находятся в активном режиме слежения и автоматически перезапускаются при каждом сохранении кода._

## 📂 Структура тестового покрытия (21 тест)

1. **Тесты UI-компонентов (`src/components/**/\*.test.ts`)\*\*
   - Проверяют DOM-события, валидацию полей ввода, логику форм, открытие модальных окон и переключение тем.
   - Находятся в папках соответствующих БЭМ-блоков для удобства долгосрочной поддержки.

2. **Системные тесты сборщика (`gulp/tests/**/\*.test.js`)\*\*
   - **CLI Automation:** валидация CRUD-генераторов БЭМ-модулей. Проверка работы предохранителя безопасности, блокирующего удаление папок с кастомным рабочим кодом.
   - **HTML Pipeline:** склейка фрагментов через `gulp-file-include` и контроль форматирования `html-beautify`.
   - **Styles Pipeline:** компиляция SCSS/Sass, верификация вендорных префиксов Autoprefixer и группировки медиа-запросов (GCMQ) в бандле `app.min.css`.
   - **Scripts Pipeline:** сборка TypeScript и транспиляция модулей в `app.min.js` с сохранением карт кода (sourcemaps).
   - **Images Pipeline:** контроль сжатия графики, автоматического дублирования в формат `.webp` и сборки SVG-спрайтов.
   - **Fonts Pipeline:** контроль физического переноса файлов и динамической генерации CSS-правил `@font-face`.
   - **Content Processor:** валидация парсинга Markdown-файлов контента и генерации динамического блога.

## 🛠️ Как создать новый тест

### 1. Тест для UI-компонента (TypeScript)

Создайте файл `my-component.test.ts` непосредственно в папке разрабатываемого БЭМ-блока:

```typescript
import { describe, it, expect, beforeEach } from 'vitest';
import { myComponent } from './my-component';

describe('MyComponent', () => {
  beforeEach(() => {
    // Имитируем HTML разметку внутри виртуального JSDOM
    document.body.innerHTML = `<div class="my-comp">...</div>`;
    // Инициализируем клиентскую логику
    myComponent();
  });

  it('should do something on click', () => {
    const el = document.querySelector('.my-comp');
    el.click();
    expect(el.classList.contains('_active')).toBe(true);
  });
});
```

### 2. Тест для функции / системной утилиты Gulp (JavaScript)

Создайте изолированный файл в директории `gulp/tests/`:

```javascript
import { describe, it, expect } from 'vitest';
import { myFunc } from '../utils/my-utils.js';

describe('My Gulp Utility', () => {
  it('should format data correctly', () => {
    const result = myFunc('input');
    expect(result).toBe('OUTPUT');
  });
});
```

## 💡 Важные технические нюансы

- **JSDOM Ограничения:** В виртуальном окружении нет реального рендеринга браузера. Сложные интерфейсные API, такие как `IntersectionObserver` или `getBoundingClientRect()`, необходимо мокать (подменять заглушками) через встроенный механизм `vi.fn()`.
- **Имитация событий:** После программного изменения свойства `.value` у HTML-инпутов в тестах, обязательно принудительно вызывайте событие обновления:
  ```javascript
  element.dispatchEvent(new Event('input'));
  ```
  Без этого внутренние нативные слушатели JavaScript не среагируют на изменения.
- **Изоляция и очистка:** Всегда переопределяйте или очищайте разметку внутри `beforeEach`, сбрасывая `document.body.innerHTML = ''`. В противном случае DOM-дерево предыдущего теста начнет влиять на логику следующего, приводя к ложным падениям.

## 🛡️ Автоматический щит контроля (Git Hooks & Deploy Protection)

- **Husky Pre-commit:** В репозиторий интегрирован автоматический перехватчик коммитов. Вы физически не сможете закоммитить код с синтаксическими ошибками или сломанными тестами.
- **Блокировка деплоя:** Запуск команд публикации проекта (`npm run deploy:gh` / `npm run deploy:hosting`) принудительно стартует сквозную проверку. Если хоть один из 21 интеграционного теста завершится с ошибкой, деплой мгновенно прервётся, защитив продакшен-сервер от багов.
