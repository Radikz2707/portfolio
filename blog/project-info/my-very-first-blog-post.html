Мой самый первый пост в блоге.

Привет всем! Если вы читаете этот текст, значит, эксперимент по созданию абсолютно всеядной, автономной экосистемы для моего блога завершился полным триумфом. Этот текст я пишу не в привычном редакторе кода VSCodium и не в разметке Markdown, а в самом обычном, классическом приложении Microsoft Word.

Как зародилась эта идея?

Когда я только начинал создавать это портфолио, передо мной стояла простая задача — развернуть красивый статичный сайт, где я мог бы делиться своими проектами и писать небольшие заметки. Первые шаги казались легкими: стек из Gulp 5, TypeScript и БЭМ-верстки работал отлично. Но как только я решил добавить полноценный блог, началась настоящая техническая драма, которая и подтолкнула меня к созданию этого робота.

Сначала файлы статей приходилось создавать вручную. Нужно было следить за спецсимволами Markdown, проверять пути и каждый раз руками копировать готовую сборку dist на сервер GitHub Pages. Стоило пользователю зайти на сайт по ссылке без слэша на конце, как относительные пути ломались, и сайт открывался абсолютно «голым» — без стилей и картинок. Вдобавок к этому, оптимизатор PurgeCSS работал настолько агрессивно, что при продакшн-сборке вырезал из файла стилей абсолютно все мои БЭМ-компоненты секций «О себе» и «Мои проекты», посчитав их лишними.

Каждый раз, когда я добавлял новый пост, мне приходилось вручную обновлять правый сайдбар с популярными статьями на всех старых страницах. Стоило забыть про одну страницу, и навигация ломалась. А браузеры пользователей намертво кэшировали старый CSS, из-за чего приходилось бесконечно нажимать Ctrl + F5, чтобы увидеть изменения.

Тогда я понял: рутина убивает желание писать контент. А что, если я захочу попросить свою девушку написать статью в блог? Нагружать её изучением синтаксиса Markdown, установкой консоли, плагинов и терминала Git — это безумие. Мне хотелось абсолютной свободы: чтобы любой человек мог просто открыть привычный Ворд, набросать свои мысли, выделить важные моменты стандартными кнопками жирности и размера шрифта, а всю сложнейшую техническую цепочку отдать умной автоматике.

Почему именно Word, а не код?

Благодаря интеграции интеллектуального конвертера Mammoth и кастомного Node.js стрима through2.obj прямо в мой gulpfile.js, проект стал полностью автономным. Больше нет никаких жестких привязок к пикселям или коэффициентам размеров. Робот сам сканирует документ Word, динамически находит базовый размер текста (даже если вся статья написана мелким 8-пиксельным шрифтом), выстраивает математическую лестницу уникальных заголовков от меньшего к большему и бережно раскладывает их по правильным семантическим тегам HTML.

Параллельно я написал умный CLI-скрипт create-post.js с искусственным интеллектом переводчика от Google. Теперь я просто пишу название темы в консоли на русском языке, а робот за долю секунды переводит фразу на чистый английский смысл для идеального URL-адреса, генерирует заготовку и сам лезет в код компонента сайдбара, чтобы встроить туда готовую БЭМ-ссылку.

При каждом деплое команда npm run deploy запускает полную очистку системного кэша компиляторов и генерирует уникальный таймштамп версии сайта. Браузер любого пользователя в мире мгновенно считывает эту метку и скачивает самые свежие стили без зависаний.

Теперь ведение блога — это чистое творчество. Робот полностью победил рутину!

Внезапный босс: Борьба с ошибкой Corrupted zip

Пока я тестировал этого «всеядного» робота, мне пришлось столкнуться с багом, который чуть не свёл меня с ума. Как только я закинул свой первый вордовский файл .docx в сборщик, консоль взорвалась страшной ошибкой: Gulp Error in Plugin: Corrupted zip: missing 1087919057 bytes [⚡].

Самое безумное здесь — это цифра. Робот утверждал, что в моем крошечном текстовом файле весом в пару килобайт не хватает... ровно ОДНОГО ГИГАБАЙТА данных [⚡]!

Сначала я подумал, что файл заблокирован самой Windows или Word не успел его сохранить. Но правда оказалась гораздо глубже, в самой архитектуре Gulp 5. По умолчанию Gulp считывает все файлы через метод src() как текстовые буферы [⚡]. Но файл .docx — это, по сути, заархивированный бинарный zip-пакет. Пытаясь прочитать его как текст, Node.js намертво ломал внутренние zip-заголовки структуры файла [⚡]. В итоге плагин Mammoth получал искажённый цифровой шум и думал, что перед ним гигантский повреждённый архив.

Я решил эту проблему красивым инженерным маневром. Вместо того чтобы мучить Gulp чтением бинарных потоков, я переписал таск так, чтобы Mammoth самостоятельно считывал файл .docx напрямую с жесткого диска компьютера через системный путь file.path, полностью минуя буферы Gulp [⚡]! Это было стопроцентное, железное попадание. Ошибка исчезла навсегда, а компиляция стала занимать доли секунды.
